# Heimdall — QA / engineering / UX pass, 26 July 2026

Static analysis only. There is no .NET SDK in the environment this was run in, so
nothing here comes from a compile, a run, or a profiler. Every finding below
cites a file and line and was read out of the tree; anything that would have
required executing the code is listed as unchecked at the end.

---

## Clean

These were checked and passed, and are worth recording so the next pass does not
redo them.

- **Layering holds.** `Heimdall.Core` contains no reference to
  `System.Runtime.InteropServices` or to Avalonia. `Heimdall.Ui` names a Linux
  type in exactly one place — `MainWindow.axaml.cs:15` (`using Heimdall.Linux`)
  and `:41` (`new LinuxPlatform(...)`). The single-seam design is intact.
- **All six `async void` handlers have catch-alls** — `OnClosing`, `OnTick`, and
  the four attached-property handlers in `Thumbnails/`. This was a documented
  crash source; it is currently covered without exception.
- **XAML is structurally sound.** All six `.axaml` files parse as XML; every
  `DataTemplate` and every binding-bearing `Style` carries `x:DataType`; all
  distinct `*Command` bindings resolve to a real command.
- **No hardcoded colours anywhere in XAML.** Zero hex literals across all six
  files. The rule that the palette comes from the desktop scheme holds without a
  single exception, which is the strongest single result in this pass.
- **Two of three caches are bounded and one disposes correctly.**
  `ThumbnailLoader` caps at 600 and **disposes the evicted `Bitmap`**
  (`ThumbnailLoader.cs:65-67`); `RowMetadata` caps at 2000
  (`RowMetadata.cs:101`).
- **The async subprocess call sites use the correct read ordering.**
  `LinuxScriptRunner.cs:126-129` starts both `ReadToEndAsync` calls and only then
  awaits `WaitForExitAsync`, which is the shape that avoids the pipe deadlock.

## UX and accessibility

Accessibility is a binding requirement for this project, so these are first.

### 1. `PropertiesWindow.axaml:65` — half a label does not scale

```xml
<CheckBox FontSize="{DynamicResource FontSizeSmall}">
  <TextBlock>
    <Run Text="{Binding Group}" FontSize="10" />   <!-- fixed -->
    <Run Text="{Binding Label}"/>                  <!-- scales -->
  </TextBlock>
</CheckBox>
```

The CheckBox does the right thing and the second `Run` inherits it. The first
`Run` is pinned at 10. This is the permissions editor, so the fixed-size half is
the owner/group/other qualifier — the part that says *which* row you are about to
toggle. Raising the font scale widens the mismatch rather than fixing it.

### 2. `MainWindow.axaml:346` — the tab close button

```xml
<TextBlock Text="{Binding Title}" FontSize="{DynamicResource FontSizeBase}" .../>
<Button Content="&#x2715;" FontSize="9" Opacity="0.5" Padding="2" .../>
```

The title beside it scales; the `×` does not. It is simultaneously the smallest
glyph in the application (9), the faintest (`Opacity="0.5"`), and the smallest
hit target (`Padding="2"`), and it is the only close affordance in the tab strip.
Two consequences follow from the code as written:

- Scaling text **up** makes this worse, not better — the title grows around a
  fixed-size target.
- A literal `Opacity="0.5"` puts the effective contrast of this control outside
  what the Plasma colour scheme can influence, which is the one case the design
  rule about not fighting the control theme was written for.

### 3. `MainWindow.axaml:63` — details-panel folder glyph at `FontSize="64"`

Decorative placeholder shown when the selection is a folder. Its `Foreground` is
correctly `{DynamicResource ViewDimText}`, so only the size is pinned. Least
serious of the three, but it sits in a panel whose surrounding text scales per
pane, so it drifts out of proportion as the pane is scaled.

### 4. Tooltip coverage is inconsistent

Sixteen `ToolTip.Tip` attributes exist in `MainWindow.axaml`, and the ones that
exist are good — they name the shortcut (`"split view  (f3)"`,
`"new tab in this pane  (ctrl+t)"`). Six glyph-only buttons have none:

| Line | Control |
|---|---|
| 243 | font-size decrease (`−`) in the view flyout |
| 275 | icon-size decrease (`−`) in the view flyout |
| 346 | tab close (`×`) |
| 376 | back (`←`) |
| 380 | forward (`→`) |
| 384 | up (`↑`) |

The three layout buttons immediately beside them (160, 170, 180) all have
tooltips, so this reads as an omission rather than a decision. The two `−`
buttons are the notable ones: they sit next to a typed-value TextBox, and the
pair is the discoverable path to a feature — per-pane scaling — that the project
treats as an accessibility requirement.

## Engineering

### 5. `MainWindow.axaml.cs:662-686` — shutdown couples two unrelated concerns

```csharp
try
{
    await _shell.StopAllSharesAsync();        // most likely to throw
    await _store.FlushAsync(...);             // most important to run
    await _store.DisposeAsync();
}
catch (Exception ex)
{
    Console.Error.WriteLine($"[heimdall] session flush failed: {ex.Message}");
}
```

Killing subprocesses and persisting the session are independent, and they are
sequenced worst-first inside one `try`. If `StopAllSharesAsync` throws, neither
the flush nor the dispose runs, and the message blames the flush — which was
never attempted. The session is crash-safe on its own timer, so the loss is
bounded to changes since the last tick, but the diagnostic would actively
mislead. Two `try` blocks, session first, would decouple them.

### 6. Three synchronous subprocess reads can deadlock before their timeout

`CopypartyShare.cs:119-127`, `CopypartyShare.cs:224-229`, `AvahiDiscovery.cs:110-113`:

```csharp
process.StandardOutput.ReadToEnd();
process.StandardError.ReadToEnd();
process.WaitForExit(timeout)
```

Both streams are redirected and read **sequentially and synchronously**. If the
child fills the stderr pipe buffer while the parent is still blocked draining
stdout, the child blocks on write and the parent blocks on read. The
`WaitForExit(timeout)` is never reached, because `ReadToEnd()` has no timeout —
so the timeout that looks like the safety net does not cover this path.

Output volume decides whether it can fire in practice. `avahi-browse -prt` is
small. The `pip install` path at 224 is the one with real exposure: it has a
300-second timeout precisely because it produces a lot of output, and pip writes
to both streams.

The fix already exists in this codebase — `LinuxScriptRunner.cs:126-129` starts
both reads first and awaits afterwards.

### 7. Timeout handling is inconsistent within one file

`CopypartyShare.cs:127` returns `-1` on timeout and leaves the process running;
the `using` disposes the handle without killing the child.
`CopypartyShare.cs:231` and `AvahiDiscovery.cs:115` both call
`Kill(entireProcessTree: true)` on the same condition. Same situation, two
behaviours, one file.

### 8. Cancellation does not kill the child

`LinuxScriptRunner.cs:129` and `LinuxSearchProvider.cs:75-93` both await with a
`CancellationToken`. When it fires, the await throws and the `using` disposes the
`Process` object — which does not terminate the child. A cancelled search leaves
`baloosearch` running; a cancelled script leaves the user's script running.
There is no `Kill` on either path (the only three in the tree are at
`CopypartyShare.cs:231`, `:391` and `AvahiDiscovery.cs:115`).

### 9. Disposal is by convention, not by contract

`SingleInstance` is the only type in the tree that implements `IDisposable`.

- `PaneViewModel.Dispose()` (`:1843`) is a plain public method. It does real work
  — cancels two `CancellationTokenSource`s, clears the Miller column, disposes
  the `FileSystemWatcher`. It is correctly called at
  `PaneGroupViewModel.cs:158`, but nothing enforces that, `using` cannot be used
  on it, and no analyzer will flag a future path that drops a pane without it.
- `CopypartyShare` holds live processes in a `ConcurrentDictionary<Guid, Running>`
  (`:27`) and implements no disposal at all. Teardown depends entirely on
  `StopAllSharesAsync` being reached from `OnClosing` — see finding 5, which is
  the one place that call can be skipped.

### 10. `IconLoader.Drawn` is unbounded where its sibling is capped

`IconLoader.cs:27` declares `Drawn` and `:26` declares `Resolved`. `Resolved` is
capped — `if (Resolved.Count > MaxResolved) Resolved.Clear();` at `:70`, with
`MaxResolved = 4000`. `Drawn` has no equivalent check and is cleared only on
theme change (`:85`). Each entry holds a rendered `IImage`.

In practice it is bounded by the number of distinct icon files a theme resolves
to, which is finite — this is an asymmetry rather than a runaway leak. Noted
because the bound is incidental rather than stated.

**Not a threading issue.** `Drawn` is a plain `Dictionary` while `Resolved` is a
`ConcurrentDictionary`, which looks like an oversight and is not: `Load` is
documented UI-thread-only (`:89-95`) and its single caller reaches it after
`ConfigureAwait(true)` (`RowIcon.cs:70-79`). `ResolveFile` is the one that runs
inside `Task.Run`, and that is the one with the concurrent collection. The pair
is correct.

### 11. Two files are large enough to be their own hazard

`ViewModels/PaneViewModel.cs` is 1,855 lines and `MainWindow.axaml` is 1,584 —
together 21% of the 16,136-line tree. This is worth naming only because the
project already has a written rule caused by it: never edit `MainWindow.axaml` by
matching a binding string, because the Miller template and the pane list bind
identically. That rule exists because the file is big enough for two unrelated
regions to look the same.

# Resolution — same day

All findings acted on. Ten files changed, one added. Static checks re-run after
every edit: six `.axaml` still parse, `x:DataType` coverage still complete, all
command bindings still resolve, brace counts balanced in every edited `.cs`.
Still no compile — the build remains the verdict.

## Two corrections to the report above

**Finding 9 was substantially wrong.** The claim that only `SingleInstance`
implements `IDisposable` came from a grep pattern that required a trailing comma,
so it missed every `class X : Base, IDisposable`. Four types implement it
correctly — `SingleInstance`, `KdeThemeProvider`, `JsonSessionStore`
(`IAsyncDisposable`) and **`PaneViewModel`**, which the report named as the main
offender and which was never at fault. The real case is smaller:
`MillerColumnViewModel` had a `public void Dispose()` without declaring the
interface. That is now declared. Both of its call sites (`Clear`,
`TruncateAfter`) were already correct.

`CopypartyShare` deliberately did **not** get `IDisposable`. `StopAllAsync`
already exists on `IFileSharing`, and finding 5 removed the path where it could
be skipped. Adding a second teardown mechanism beside a working one is the kind
of redundancy this project avoids on purpose.

**Finding 6 undercounted.** The report said three sequential-read sites; there
are five. `DesktopEntries.cs:57` and `LinuxRemoteMounts.cs:206` have the same
shape and were missed. `DesktopEntries` is the more interesting of the two — it
carries a comment explaining that stderr is drained rather than ignored *because
a full stderr pipe would block the child*, which is exactly right about the
hazard and does not avoid it, since stdout is still drained to completion first.
Both are fixed. There are now zero synchronous `ReadToEnd()` calls in the tree.

## Deliberately not done

**Finding 11 — file size.** `PaneViewModel.cs` at 1,855 lines and
`MainWindow.axaml` at 1,584 are real, but splitting them is a refactor with no
functional gain, no test suite to catch a mistake, and no compiler available here
to check the result. Doing it badly is worse than leaving it. It is a reason to
be careful when editing those two files, which the handoff already says.

## Behaviour that changes visibly

- The details-panel folder glyph renders at 84 rather than 64 at default scale,
  because `TileSize` is the icon-scale metric it now follows.
- The tab close `×` is larger, has a bigger hit area, and takes its dimness from
  the colour scheme rather than a fixed 50% opacity.
- Permissions qualifiers in the properties window render at 11 rather than 10,
  and now grow with the font scale.
